# File Uploads (Validated Storage + Signed Downloads)

Reference contract for `saas_templates/<lang>/file_uploads_<lang>.<ext>` in all eight languages. Every
language implements the same functions, error codes and return shapes, so the same input gives the
same answer everywhere. Common rules for every system are in [README.md](README.md).

## Required tests

Each language's tests file has at least one test for every id below, and names the id in the test's
name or in a comment on the line above it (for example `# UPLOAD-01`), so a missing case is visible.

| id | what it proves |
|---|---|
| `UPLOAD-01` | a .exe is rejected; a .exe renamed to .png is rejected by its magic bytes |
| `UPLOAD-02` | a real PNG is accepted and stored under a generated name, not the original |
| `UPLOAD-03` | "../../etc/passwd.png" is stored safely; the display name has no path parts |
| `UPLOAD-04` | a file over the size limit is rejected |
| `UPLOAD-05` | a non-member of the org cannot upload or download |
| `UPLOAD-06` | an expired link is rejected; a link with one changed character is rejected |
| `UPLOAD-07` | after delete_file, the file can no longer be linked or downloaded |

## Contract

```text
Source: OWASP File Upload Cheat Sheet (CC BY-SA 4.0 -- rules applied, text not reproduced).

PURPOSE:
  Accept user uploads safely, store them, and serve them through expiring signed links.

SCHEMA:
  files (id, org_id, owner_user_id, stored_name, original_name, extension, mime_type, size_bytes,
         sha256, created_at, deleted_at NULL)

ENDPOINTS / FUNCTIONS:
  upload(user, org_id, original_filename, bytes, declared_content_type) -> {file_id} | error
  create_download_link(user, file_id, ttl_seconds=300) -> signed URL/token
  download(user, token) -> bytes | error      (the caller is needed to re-check access; amended 2026-09-26)
  delete_file(user, file_id) -> soft delete

IMPLEMENTATION -- RULES (from the cheat sheet):
  - Extension ALLOWLIST (default: pdf png jpg jpeg gif txt csv docx xlsx). Anything else rejected.
  - Do NOT trust the Content-Type header ("it can be spoofed"). Check the file's SIGNATURE (magic
    bytes) matches the extension, using the FULL signatures: PNG 89 50 4E 47 0D 0A 1A 0A,
    JPEG FF D8 FF, GIF "GIF87a" or "GIF89a", PDF "%PDF-", ZIP-based docx/xlsx 50 4B 03 04.
    Text types: reject if they contain NUL bytes. (Amended 2026-09-26: the first version gave 4-byte
    PNG/GIF prefixes, shorter than the real signatures.)
  - "Change the filename to something generated by the application": store under a random id.
    The original name is only kept for display, sanitised (strip path parts / .. / control chars).
  - "Set a filename length limit" (255) and "Set a file size limit" (default 10 MB, configurable).
  - "Only allow authorized users to upload files": caller must be a member of org_id.
  - "store them outside of the webroot": a configurable storage directory, never under public/.
  - Download links: HMAC-signed over (file_id, expires_at), compared in constant time, expiring.
    download() also re-checks the caller may see the file.
  - A malformed token (bad encoding, wrong number of parts, non-numeric expiry) is an ordinary
    "invalid link" error, never an unhandled parse exception.
  - A deleted file: create_download_link and download both fail with not-found.
  - Storage is behind the injectable store (BUILD & TEST CONTRACT); file BYTES go to the configured
    storage directory -- tests use a temporary directory.

TESTS:
  - **UPLOAD-01** a .exe is rejected; a .exe renamed to .png is rejected by its magic bytes
  - **UPLOAD-02** a real PNG is accepted and stored under a generated name, not the original
  - **UPLOAD-03** "../../etc/passwd.png" is stored safely; the display name has no path parts
  - **UPLOAD-04** a file over the size limit is rejected
  - **UPLOAD-05** a non-member of the org cannot upload or download
  - **UPLOAD-06** an expired link is rejected; a link with one changed character is rejected
  - **UPLOAD-07** after delete_file, the file can no longer be linked or downloaded
```
